# 代码阅读路线（配合动手实验）

> 目标：按"启动 → 驱动 → 任务 → 日志 → 报警/健康 → 控制台"的顺序读，
> 每读一块就做一个可观察的小实验，避免"看懂了但一改就崩"。

---

## 0. 阅读前的准备

1. 打开 `MDK-ARM/demo2_1.uvprojx`，先 Rebuild 一遍，确认 0 Error / 0 Warning；
2. 串口助手 115200-8-N-1，能看到每 3 s 的监测行；
3. **调试前关掉看门狗**：`App/system/health.c` 顶部
   ```c
   #define HEALTH_IWDG_ENABLE 1   →   0
   ```
   否则断点停 >2 s 会被复位（验收时再改回 1）；
4. 建议在 `Options for Target → Debug` 里把 ST-Link 的 Reset 设为 `Autodetect`，
   下载后按 F5 全速跑，先看现象再下断点。

## 1. 第一遍：把"启动链路"走通（约 30 分钟）

| 顺序 | 文件 | 重点看什么 |
|---|---|---|
| 1 | `Core/Src/main.c` | `HAL_Init()` → 时钟 → 外设 → 调度器前初始化 → 创建任务 → `vTaskStartScheduler()`；**为什么所有创建都在调度器之前** |
| 2 | `Core/Src/stm32h7xx_it.c` | `SysTick_Handler` 只调 `xPortSysTickHandler()`；`TIM7_IRQHandler` 喂 HAL tick；`EXTI0/EXTI15_10` 只转发 |
| 3 | `Core/Src/stm32h7xx_hal_timebase_tim.c` | HAL 的 1 ms 时基如何被 TIM7 接管 |
| 4 | `User/FreeRTOSConfig.h` | `configTICK_RATE_HZ`、`configMAX_PRIORITIES`、heap 48 KB、`configLIBRARY_MAX_SYSCALL_INTERRUPT_PRIORITY=5` |
| 5 | `BSP/LED/bsp_led.c` | `HAL_TIM_PeriodElapsedCallback` 里 TIM7/TIM6 两个分支；呼吸/闪烁状态机 |

**读完要能回答**

- 为什么 HAL 时基不能和 FreeRTOS 共用 SysTick？
- 为什么 `SysTick_Handler` 里不能再调 `HAL_IncTick()`？
- 为什么 TIM6/TIM7 中断优先级必须是 5？

## 2. 第二遍：一条数据是怎么从传感器走到 Flash 的

| 顺序 | 文件 | 重点看什么 |
|---|---|---|
| 1 | `BSP/i2c/bsp_i2c_bus.c` | 互斥量 + "调度器启动前不加锁" 的特殊处理（BASEPRI 坑） |
| 2 | `BSP/sensor/bsp_ap3216c.c` / `bsp_mpu6050.c` | 统一的 `Take → 读寄存器 → Give` 结构；返回码约定（0 = 成功） |
| 3 | `App/sample/sample_task.c` | ENV 10 Hz / MOT 20 Hz；`Sample_t` 32 B 的组装；`xQueueSend(...,0)` 满则丢并计数；`Alarm_Feed*` 的 `valid` 参数 |
| 4 | `App/log/log.c` | `LoggerTask` 双队列收集 → `Log_WriteBatchLocked` 页切片/擦除/回读 → `Log_CommitMetaLocked` A/B 轮换 |
| 5 | `App/log/log.h` | 32 B 布局、Flash 分区、批量参数 |

**读完要能回答**

- 为什么 I2C 访问不能放在 `taskENTER_CRITICAL()` 里？
- 队列满了为什么是"丢点 + 计数"而不是阻塞采样任务？
- 一批 32 条为什么正好是 1 KB？它跨几页？
- 掉电发生在"数据写完、检查点没提交"时，恢复流程靠什么把数据捞回来？

**实验 A：观察丢点**
```
> logpause on
（等 8 s，看 status 的 drop 增长）
> logpause off
> status
```
预期：`drop` 先线性增长，恢复后停止；`q` 回到 0。

- 为什么 UiTask 的蜂鸣器相位要在报警触发瞬间清零？
- 为什么 HealthTask 的优先级是 1（最低）？

## 5. 第五遍：自己动手改（每次只改一处）

| 实验 | 改哪里 | 观察什么 |
|---|---|---|
| 优先级反转 | `main.c` 把 `MOT` 从 5 改 3 | 采样是否开始丢点、`drop` 是否增长 |
| 队列深度 | `sample_task.h` 的 `SAMPLE_QUEUE_LEN` 128 → 16 | `logpause on` 后多快开始丢点 |
| 确认窗 | `alarm.h` 的 `ALARM_CONFIRM_LIGHT_SAMPLES` 10 → 3 | 遮光多久就报警（应 ≈0.3 s） |
| 栈溢出 | `main.c` 里 LED 栈 128 → 64 | 串口打印 `!! STACK OVERFLOW: LED`，2 s 后 IWDG 复位 |
| 去掉总线锁 | `bsp_i2c_bus.h` 的 `I2C_LOCK_TEST_SKIP` 0 → 1 | 并发 `sensor` + `cfg save` 时偶发 NACK（flags ERR 位） |

> 每次改完只烧一次、只观察一个指标，然后 `git checkout -- <文件>` 还原。

## 6. 阅读时最容易卡住的 6 个点

1. **`configPRIO_BITS` 为什么写死 4**：CMSIS 的 `__NVIC_PRIO_BITS` 是 `4U`，armasm 不认 `U` 后缀，会报 `A1586E`。
2. **`__set_BASEPRI(0)` 那行是干什么的**：调度器启动前创建 RTOS 对象会进临界区，`uxCriticalNesting` 的哨兵值让退出判断失效，BASEPRI 卡在 0x50，TIM6/TIM7 全被屏蔽。
3. **任务通知不是"信号量"**：它是直接写在 TCB 里的计数，`ulTaskNotifyTake(pdTRUE, …)` 会一次清空；所以醒来必须把缓冲区取干净。
4. **`vTaskDelayUntil` 的初值**：必须取进入循环前的 tick，不能写 0。
5. **`EVT_FLASH_BUSY` 为什么几乎看不到蓝闪**：一批写盘只要几毫秒，UiTask 50 ms 才轮询一次。
6. **`dump` 的索引**：`Log_GetAvailable()` 是"可读窗口"长度，`first = avail - count` 才是最近 n 条的起点。
